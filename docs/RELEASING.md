# Maintainer release steps

WristLab is a growing platform. A repository release is a snapshot of the foundation and selected bundled examples, not a promise that every experiment or future project is production ready.

1. Update the changelog and per-project maturity/evidence. Verify image/font rights and permission declarations.
2. Run `tools/test.py`, `tools/test_projects.py`, `tools/catalog.py check`, and `tools/check_publication.py` with Python. Build selected targets or `python3 tools/build.py all` using the intended signing configuration.
3. Confirm the latest commit's GitHub Actions run is green. CI uploads development APKs for inspection; it does not publish a Play Store app or deploy anything to devices.
4. Choose a version tag. For early releases, use a prerelease such as `v0.1.0-alpha.1` and clearly label APKs experimental. Record the commit.
5. Upload only the intended APKs and `build/apks/SHA256SUMS` to a draft GitHub release. Never upload build directories, signing keys, passwords or device logs. Inspect filenames and checksums, then publish the release.
6. Link setup instructions, compatibility, known limits and contribution steps in release notes. A source archive is generated by GitHub from the tag.

The first public snapshot uses a local development key, separate from the original device installation. Each clean CI job creates its own development key. Their APK signatures can differ even when the source is the same. For compatible updates over time, maintainers must keep a consistent signing key in private storage and use the signing environment variables in BUILD.md; that key must never be committed. A new public signing policy should be documented before claiming an update channel.

The SDK setup action explicitly installs `platform-tools` rather than its obsolete default `tools` package. JVM and publication checks run before SDK setup so an infrastructure failure does not hide their results.
